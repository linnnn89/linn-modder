# CK3 MOD 制作技巧

从萌战 MOD 最初三人原型到大规模角色迁移、婚姻与轮回、文化宗教、作弊菜单和 DLC 兼容的实际工作中提炼。本文整理的是可复用做法，不是功能宣传或旧故障待办。依据包括六条开发对话、当时日志和存档调查、当前生成器与产物，以及下方列出的作者资料。

**基础经验基线为 CK3 1.20.0.4；第27项为2026-10-17补录的1.20.1.1决议控件崩溃。** “日志确认”“用户实测”“代码检查”“设计约定”分别说明依据；旧版修复不能自动算作新版全量验收。`status: in-progress` 表示部分玩法与组合尚未完成运行验收，不表示本篇仍是空白计划。

## Setup：先确认正在改哪一份

每次接手先确认游戏精确版本、启用 DLC、播放集顺序、MOD 描述文件中的路径，以及本轮实际存档。Windows 的 Documents 可能迁移或重定向；Steam 游戏和 Workshop 也可能分布在不同盘。通过启动器配置和 Steam 库信息查实际位置，不硬编码用户名或盘符。

分清四份内容：**生成源与清单 → 工作区 MOD 产物 → 实际安装目录 → 发布包**。同一个版本号可能包含后续修订，版本字符串不能替代文件哈希；旧 ZIP 也不能证明安装目录已更新。游戏与 Workshop 原包作为读取依据，修改写入自己的 MOD。

先看 `descriptor.mod`、外部 `.mod` 注册文件、依赖名称和实际加载路径，再追脚本。不要凭“文件已经复制”判断启动器加载了它。大包还要核对角色清单、头像清单与生成器的来源，不以旧 README 的人数作为事实。

## Route：优先借用本版原生机制

通常走 CK3 自有的 `common/`、`events/`、`history/`、`localization/`、`gui/`、`gfx/`，通过自有命名空间实现内容。遇到陌生接口，按以下顺序核查：

1. 本版 `game/common/` 的 `.info`、同功能原生脚本、实际调用者和日志。
2. 本版可导出的效果、触发器和数据类型文档；在有游戏操作授权时，用调试控制台的 `script_docs`、`dump_data_types`，检查实际生成位置及版本。
3. 官方说明、工具作者源码、维护者文档与明确版本的 MOD 实现。
4. 编写一个小样本，跑原操作流程，再扩大到全体角色或整个领国。

原生脚本是调用实例，不能仅因某个单词出现过就移到任何作用域。第三方 MOD 展示了一种路线，也不证明它兼容本版。已经有自己的生成器时修生成源，避免手改产物后下一次构建又恢复错误。

## How the game works：先分清数据层

| 数据层 | 负责什么 | 常见误会 |
|---|---|---|
| 历史和书签 | 初始人物、头衔持有人、日期、推荐入口 | 改历史会自动重建旧档；书签名就是实际玩家 |
| 数据库定义 | 文化、信仰、教义、传统、特质、CB | 文件键一定能直接取得旧档中的运行时对象 |
| 运行时对象 | 当前身体、文化实例、配偶、头衔、局势 | 同名就是同对象；新身体就是旧角色复活 |
| 事件与效果 | 操作目标、结算、后续事件 | 菜单显示成功就等于数据已写入 |
| 本地化与 GUI | 文案、提示、画像、点击行为 | 翻译键和事件 ID 是一回事；正确图片一定被界面使用 |
| 存档持久状态 | 已生成的人物、关系、队列、规则值 | 重启会按新默认值重置所有已保存状态 |

对一次操作写清 **执行人、目标人、目标国家、结果字段**。对一次迁移写清 **稳定角色身份、当前身体、所属家族、现任领主**。这些字段越早分开，后面的轮回和兼容越容易维护。

## Build steps：一个小功能的完整落地顺序

1. 从用户当前操作与最新日志开始，确认实际加载文件；新局问题不套用昨晚旧档的结论。
2. 找一个本版原生例子，标注输入作用域、对象条件、写入效果、回调及预期输出。先确认接口存在，不发明像 `add_marriage` 这样的名字。
3. 给新内容分配稳定 ID、命名空间和自有文件；改原生对象时列明最小覆盖范围和版本基线。
4. 修改生成器和产物。内容清单同时驱动历史、轮回模板、画像映射与菜单；人工润色文本要保留可重复构建的来源。
5. 做针对性结构、引用、作用域和部署核对；存在旧档变化时检查相应迁移，而不是全库清空重建。
6. 按 Verification 中与改动相符的一条流程验收。记录本轮实际做过的检查，完成后停止。

## Gotchas：踩过的坑与处理方法

### 1. 按钮可点、金钱有效，属性却不变

**现象：** 自己与其他角色都能进菜单，加点后面板没有变化。调查一度依据旧档中基础属性已到上限解释新局故障，用户后来明确表示已重开。

**原因与处理：** 这是需要逐层拆分的调用链，不能预先归结为“上限”。核对本次新档、角色 ID、菜单保存目标、事件根作用域、`var:` 所属对象和实际 `add_*_skill` 调用。萌战修订移除了作弊执行链上无关规则和重复授权判断，直接作用于已选择对象。随后用户实测确认：推进时间后属性会更新。

**留下的规矩：** 区分“效果没执行”“修改了错误对象”“面板未刷新”“基础值达到限制”。在本项目加点页保留简短的时间推进提示；不要据此宣布所有 CK3 效果都延迟一天。用同一人物操作前后字段、推进时间与存读档验证，必要时比较基础值和最终面板值。

### 2. 一个开局规则关闭，多个无关功能消失

**现象：** 关闭召集萌誓角色的规则后，作弊、婚姻或文化入口跟着失效；玩家亲自操控登记角色时又被当作不合法目标。

**处理：** 沿“是否显示 → 是否可用 → 进入事件 → 最终效果”检查所有条件。通用作弊独立于名册管理、轮回初始化和召集规则；强制玩法只保留执行所需的对象条件。规则是否启用、玩家身份、普通求婚条件、轮回去重分别管理。

**验证：** 规则开/关 × 自己/他人 × 普通玩家/登记角色。不要只在一个默认新局测试。存在有效目标、避免生成重复化身是机制条件；没有设计理由的文化、婚姻主角或首日初始化门槛不应混进加点功能。

### 3. 事件 ID 没有字面重复，日志却报告冲突

**本项目证据：** 一次日志调查发现 1,117 项事件冲突；相关批次有 1,118 个高于 9,999 的事件编号。字典去重与“引用都存在”的静态检查没有发现它们。

**处理：** 本项目将数字尾段限制在 `0..9999`，通过多个命名空间划分菜单族；例如编写期的 `mz_ss.160740` 转为 `mz_ss_ui_16.740`。保留旧的低位 ID，统一改定义、调用和 namespace 声明。本条是本版工程约束，不猜测引擎内部的具体折叠算法。

**验证：** 检查数字范围、声明、唯一性和完整调用图，再查看重启后的引擎冲突日志。事件 ID 与 `mz_ss.160740.t` 这样的文本键分开处理，不用全文替换误改字符串、注释和历史姓名。改号前另查存档中是否存在待触发事件；修改脚本引用不能自动迁移旧档队列。

### 4. 括号正确，动态描述仍让启动卡住

**日志确认：** 1.20.0.4 中把 `first_valid` 直接嵌进 `triggered_desc`，会反复报解析错误。该位置接受 `trigger` 和 `desc`；这不等于所有位置都禁止 `first_valid`。

**处理：** 按本版原生结构拆成互斥描述分支，同时修生成器和生成文件。回归检查针对直接子项，不能仅数括号，也不能全文禁用一个合法关键字。

**结果：** 早期修复已有实际到达主菜单的证据；该结果只覆盖启动问题。详细错误、最小结构和验收记录见已有的[动态描述加载失败案例](../../../skills/linn-modder/anime-strategy-mod/references/ck3-dynamic-description-loading-failure.md)，不在这里重复旧排错日志。

### 5. 存档有文化，`culture:键名` 却取不到

**日志与存档确认：** 某旧档存在 ACG 文化实例，但转换脚本报 `Failed to fetch a valid culture 'mz_ss_acg'`。改信成功不能证明文化转换也成功。

**处理：** 当直接命名引用在该档失败时，从运行时文化列表解析对象。本项目用专属 heritage、language、ethos 三个支柱匹配并保存 culture scope；当时存档唯一匹配到目标。以后扩展混合/分离文化时，要重新检查该匹配是否仍唯一，不能把它当作所有文化都可靠的通用主键。

**验证：** 转换人物、领地、革新继承和文化接纳使用同一对象；检查实际结果与日志。不要硬编码某份存档里的数字文化 ID，也不要在未取到对象时仍发成功通知。当前部分新增脚本仍采用直接文化引用，应按其执行上下文分别验收，不能由这次修复推断全项目同类引用都已解决。

### 6. 提示框反复解析尚不存在的运行时对象

**日志确认：** 文化决议曾在说明预览中产生数万次对象解析报错，日志增长到数十 MB。预览失败和实际执行失败是两条证据，不能相互替代。

**处理：** 显示稳定的 `custom_tooltip` 文本，实际对象解析和写入放在执行效果里；必要时使用 `hidden_effect` 避免预览模拟读取未建立的临时对象。它不是忽略错误的开关，执行所需作用域仍须正确。

**验证：** 打开决议但不点击，观察是否新增重复错误；点击后再核对状态。轮回变量保存在游戏状态里不等于每次轮回都新建一个日志文档；空间问题先看具体日志、存档数量及增长来源。

### 7. 写错回调名，或者把 faith 当 rite

**本项目错误：** 初始化曾写成 `after_lobby`，正确入口是 `on_game_start_after_lobby`；教义选取条件一度在 faith scope 使用了 rite 判断。

**处理：** 回调按本机 `common/on_action/` 定义逐字核对。通过原生钩子的 `on_actions` 列表挂接自有回调，逻辑写在自己的名字下面，不随手替换原生 effect。根作用域、预存 scope、是否按角色调用都读本版注释。

`yearly_global_pulse` 在本版说明中没有角色 root；不能把它直接当玩家事件。当前宗教结构包含 religion、faith、rite 以及独立 `tenet_types` 等数据库；旧教程中“宗教对象”的模糊说法不足以确定参数类型。

巡检尽量围绕登记槽位或待处理队列，只在必要时遍历全世界；不要让每名角色的回调再扫描全部角色。首日初始化、死亡通知和低频补漏分别负责各自工作。判断卡顿前先计数扫描次数和日志增量，不能只因角色库变大就认定是图片或轮回拖慢。

### 8. 缺家族、空名字、本地化冲突是不同问题

**本项目证据：** 人物引用了 19 个未定义共享家族，另有 22 个家族名称为空；还发现与其他 MOD 字面不同的显示键发生引擎哈希冲突。

**处理：** 校验整条链：人物引用 → dynasty/house 定义 → 名称键 → 对应语言非空文本。共享家族要按实际被引用的集合生成，不能只为每位人物生成个人家族。对引擎报告的哈希冲突改显示键及其调用，不随手改已保存人物的历史姓名键。

**验证：** 定义存在、名字非空、关系一致、引擎不再冲突分别检查。事件定义冲突、本地化字面重复和本地化哈希冲突分开统计。旧档缺失家族的修复只补缺，不能把玩家已经有效的家族关系全部重置。

### 9. 书签是女领主，进游戏却成了另一个人

**早期根因：** 在初始化未完成时运行授地效果，推荐人物实际仍无地，游戏选中了原头衔持有人。

**处理：** 可选开局的人物和土地在正确日期的历史层落实；运行后再登记名册。检查头衔 ID、首府地产、持有人、上级、政体和起始日期。中文地名与内部 ID 分开，不能凭翻译地名判断县不存在。

**验证：** 点击书签进入地图，核对真正的玩家和持有头衔。新增历史只在新局读取；旧档读取测试不能验证新历史。大批分配县时先算可用数量与已有占用，不能为新角色覆盖旧角色领地。

### 10. “永生”“死亡阻止”“轮回”不是同一功能

**用户实测：** 早期食蜂被刺杀后能生成在世化身并保留故事进度，但新身体一度进入了错误家族。永生特质并未阻止所有脚本死亡。

**处理：** 用稳定角色槽位记录身份，槽位再指向当前身体；开局和重建共用同一初始配置。长期故事、计数、队列和原配偶引用不要只存在身体上。创建前检查当前有效化身，避免读档、回调和定时巡检重复生成。

轮回是创建新对象，不冒称原角色原地复活。家族、原配偶、宫廷、领地、后天成长分别约定。不要把管理者或玩家继承人自动当成原丈夫；NPC 重建也不能解决玩家死亡后 Game Over 的所有情形。

**项目约定：** 不迁移孕期。原身体和已经发生的家谱历史保留；新身体回原有家族。完整亲子重连与自动夺回领地只有明确实现并验收后才写入功能说明。

### 11. 同作品不等于亲属，同宫廷不等于永不离开

**处理：** 朋友、恋人、收养、师徒、生物父母、家族和政治从属分别建模。真正姐妹需要可解释的共同父母；养姐妹不强填共同生父。未知亲缘留空，不凭相似姓氏补齐。

一份 manifest 维护角色键、原作身份、同名别名、关系边、家族键和阵营。初始化和轮回都读取它。校验父母年龄、死亡日期、循环亲缘、头领等级以及实际 employer/liege；原作事实与中世纪架空据点分列。

人物成为朋友或初始廷臣不代表原版后续迁廷一定被阻止。团体凝聚的实际策略需要玩家确认范围，不能为了留人把所有同作品成员硬写成亲属或一律互为朋友。

### 12. 素材数、人物数、作品数容易混算

源包可能同时包含正式人物、不同服装、变体、匿名图片和 NPC。曾出现“74 套图”被误当作“74 名女性”的风险；另有同名跨作品和中文别名重复。

**处理：** 用来源包 ID＋人物记录 ID 建立映射，另存画像变体与作品别名。区分 `record`、`variant`、`image_only`、`npc`。作品分类统计口径明确，不能把字符串去重的结果混作规范作品表数量。

身份不明不凭文件数量自动新增角色；用户要求按来源 TAG 迁移时遵循既定素材范围，不重复审核整批旧图。缺图是否另找、排除哪些系列属于当轮项目约定，后续授权可以改变，不能写成工具的永久禁令。

### 13. 独立头像完整，游戏仍只显示头发

**用户截图与代码核对：** 曹操、牧濑红莉栖等原画面部较低；婚舰通用库另一个 GUI 定义使部分小控件继续截取大立绘，绕过了新 DDS。仅看离线拼图发现不了这条调用路径。

**处理：** 先从截图定位实际控件类型，再查所有启用 MOD 中的同名 GUI 定义和加载顺序。本次调整了小头像定义的加载位置；登记角色走独立 bitmap，普通人物保留原生分支。不要概括成“所有 CK3 文件都最后加载覆盖”，不同数据库/GUI 的规则要分别核查。

**验证：** 在实际关系栏、人物列表、配偶栏等出问题位置看图；并测试点击、右键、悬停、死亡/囚禁状态。用户确认过一轮头像改善，不等于之后新增全角色和所有控件都已验收。

### 14. 一套居中裁框不能适配所有立绘

优先复用源包已有头部图；没有时按完整面部测量，保留额头、双眼、鼻口与下巴。头发、武器、翅膀与透明留白都会改变“整图中心”，不能用胸腰或整图中心代替面部位置。

主立绘、头部头像、肩部控件和预览图分别定义用途，保留原始素材与裁框。检查目标遮罩和实际渲染尺寸，不把某一次用过的 `256×320` 当作所有 CK3 图片的硬性规格。原画的眼饰/符纸等遮挡不等于裁切失败，除非用户要求不要擅自重画。

**2026-10-17 制作参考补充：** 已将二向箔安装包教程、GENSEKI 日文立绘规范、Konado 素材/锚点文档及 Ren'Py 等比缩放说明汇入 [CK3 二维立绘与独立小头像参考](../../../skills/linn-modder/anime-strategy-mod/references/cast-and-assets.md#ck3-二维立绘与独立小头像制作及审查参考)。二向箔当前默认 mesh 的参考焦点约为画布 `(0.5W, 0.2H)`，其作者脚本使用 `ground_joint`；`contain/top` 只保证等比容纳，并不保证人脸落在这个焦点。小头像要另外检查实际遮罩与底部数值条。外部服务的画布、半身范围和建议比例不能当 CK3 通用限制；离线预览和接线检查仍不等于当前版本游戏验收。

### 15. ACG 路人与自创人物失去原生 3D 外貌

**当前代码确认的根因：** 把文化默认 ethnicity 全部设为 `anime_ethnicity`，导致没有专用画像映射的新生、随机和自创人物也进入纸片人路径。

**处理：** 普通人口使用原生 ethnicity，登记角色显式绑定二次元身份与画像。旧档修复只找“误用旧 ethnicity 且没有有效 2D 画像”的角色；同时尊重 Anime Core 及共存 MOD 的画像判断链。不能只排除自家角色后重置所有其他人物。

本项目修复选择 `asian_japanese`，它是本项目的美术默认，不是所有文化的通用选择。该修复已完成静态和安装核对，普通人口、角色设计器与共存 MOD 的游戏画面仍要各自验收。恢复 3D 路径不等于恢复此前已丢失的自定义 DNA。

### 16. 多婚教义显示很高，天朝仍只能有一位正式配偶

**代码与存档证据：** “宫闱权谋”传统的正式配偶参数覆盖了信仰人数。修订该项后，后续存档曾确认七位正式配偶，原配偶仍在。

**处理：** 核对文化传统、宗教教义与政体 UI 三层。该补丁让正式配偶上限回到宗教计算，保留侧室、宦官与宫廷功能；因此影响拥有该传统的全部人物，而非仅某个玩家。`number_of_spouses = -1` 在相关接口中不是“无限”的同义词，必须读参数说明。

`marry` / `marry_matrilineal` 是本版正式婚姻效果；恋人关系和自定义誓约不能替代配偶。未确认的 `set_relation_spouse`、`add_marriage` 或 `force` 参数不要编造。不要为了成功先离婚、替换或删除已有配偶。

**验证：** 比较完整配偶集合，而非只看主配偶头像；再查侧室集合、主配偶与存读档。失败时显示实际人数和引擎允许上限；没有满额时不能一律报“已达上限”。

### 17. 兼容女性从者，别拆掉她的角色身份

圣杯战争兼容需要核对本机从者 trait、禁婚/禁育状态及其持续维护逻辑。身份、永生、职业能力和 `celibate` / `devoted` 等状态不是同一职责。

本项目做法是识别目标后，在婚约流程中处理已确认的阻碍项，成功后核对原生配偶关系，失败恢复本次临时改动。不能移除整个从者身份来解除禁婚，也不能删第三方特质后假定后续事件不会重新加回。

本地脚本兼容已接入；具体从者、后续维护和生育流程仍需实际验证。兼容别的 MOD 现有角色，不等于把其整套资源复制进本包。

### 18. 怀孕不是加一个 trait，位置不是宫廷归属

**本版接口调查：** 怀孕涉及孕期、生父/名义父亲和后续出生流程。调用原生怀孕效果并明确生父，检查孩子出生后的关系；仅增加/删除 `pregnant` 不能视为完整怀孕/终止流程。

召唤也要区分 location、employer 与 liege。有地统治者保留领地并移动位置，不等于变成玩家廷臣；同级或更高统治者不能简单赋成封臣。等级调整要处理不低于玩家等级的头衔，再结算剩余领地及下属；仅改一个引用不代表整个政治关系已完整更新。

### 19. 宗教分支与文化改革，要逐项说明继承条件

被写进教义/传统的常驻修正通常随实际持有该项的对象生效；角色个人修正、定时事件和只判断原始 faith ID 的脚本另算。想让萌教分支也使用，按需求检查 religion 范围和当前教义，不能在文案上说“继承”，代码却限定原始信仰。

本版核心教义使用 `common/religion/tenet_types/`；本项目已有一次 faith/rite 作用域错误。文化传统的常规选择、混合文化与分离文化是不同路径，核对各自入口，不能假定 `is_shown` / `can_pick` 自动覆盖全部路径。

六槽方案分三层：引擎共享上限、玩家界面槽数、AI 创建规则。当前项目共享上限为六，界面规则显示三/六；关闭玩家规则不会把 AI 上限恢复为三。新增旧档规则、默认未选教义/传统与已保存配置也分别处理。

### 20. DLC 开关能挡执行，不一定能挡解析

天朝菜单将个人功绩、个人资金、玩家所属朝廷、皇帝国库分别指向正确对象。先复用同版原生任免/解职效果，保留职位关联和继任清理；只要取消处罚就只改处罚，不截断正常职位流程。

DLC 专用菜单和效果放独立文件，入口用本版 DLC/对象条件。若引擎解析时不认识某符号，外层 `if` 不一定能救；先确认接口属于基础版本还是仅 DLC 内容。普通角色、天朝角色、未启用 DLC 三种环境各自验证，不能以“不点就行”直接宣布无 DLC 兼容。

### 21. 救灾不能只删几个负面 modifier

**本机代码研究形成的路线：** 地震/洪水涉及 situation、受灾县、参与者和恢复工程。先收集玩家领国内受影响对象及工程快照，再按原生完成流程处理；同步更新参与者与后续恢复状态。县效果按已确认灾害来源清理，不清空所有负面修正。

跨境灾害只移除本国受灾范围；还有外国受灾县时不结束整场局势。封臣救灾不能顺带替最高宗主完成全帝国工程。原生结束事件可能有 scope/变量和弹窗后续，不要直接发一个“结束事件”就认为完整结算。

当前“强效救灾”实现只覆盖地震、洪水及指定次生灾害；没有确认瘟疫的可靠终止路径，介绍就不写能清瘟疫。静态检查通过也不能替代受灾局内点击验证。

### 22. 宣战要求展示与胜利结算必须对应

CB 要同时维护显示/可用条件、代价、胜利与失败、目标集合、停战及标题文案。“进攻方要求”负责让玩家看懂，真正交接仍由胜利效果执行。

“夺回圣地”“吞并最终宗主全国”“带回配偶及其领地”是三个不同目标集合。老婆归家先收集同一防守领国内目标，按等级处理头衔，再移动从属；不能套用整国征服顺带吞掉无关封臣。执行过程中改 liege 会影响后续枚举，因此先快照再结算。

同教派参战要检查实际战争对象、阵营和有资格加入的统治者；是否自动加入与是否开放加入是不同设计。测试和平结果、实际头衔与封臣、费用、停战，而非只验证 CB 出现在列表中。

### 23. “修好了”却被下一次生成或另一聊天覆盖

**本项目发生过的风险：** 角色迁移、头像和玩法同时修改主本地化与 README；安装副本与工作副本有各自的新内容。照旧快照整包覆盖会丢失刚完成的修改。

**处理：** 独立功能优先使用独立文件；共享文件按键/语法块局部更新，修改前重读哈希与差异。若基线改变，先合并再安装，不回滚别人工作。生成器、生成产物和人工文案均有来源；验证不相关部分保持原字节，必要时比较结构而非归一化全文件。

旧生成器曾带有 `CRCRLF` 特殊换行，读取后全量重写会造成巨大差异。先识别编码和换行，按本轮必要范围修改。解析嵌套脚本时识别注释、字符串和括号深度，别用“每行以键开头”的正则把内部 `if` 当顶层定义。名字池匹配还要锚定字段，避免 `MALE` 误匹配 `FEMALE`。

### 24. 旧档兼容不是一句“重启即可”

对照变更类型决定处理方法：

| 变化 | 通常需要的处理 |
|---|---|
| 菜单文本、已存在特质/传统的定义 | 重启加载新资源，再查旧档内实际持有情况 |
| 新人物、初始头衔与书签历史 | 新开局；需要旧档补入时另写明确迁移 |
| 新规则默认值 | 检查已保存规则，不能假定旧档自动采用新默认 |
| 新增缺失家族或缓存引用 | 幂等补缺入口，保留现有有效数据 |
| 改稳定 ID、事件编号或角色引用 | 查存档持久字段与待执行队列，制定迁移或保留旧入口 |

修改存档前确认文件名、实际游戏日期、玩家/角色 ID、压缩格式并备份；对比修改字段和未改部分。用户已经新开局时必须切换证据，不能一直引用旧档。未获“改存档”任务时，读档排查不顺手写回。

### 25. 原生参数名、数字与方向都要查证

`popular_opinion` 曾被误用，后改为本版实际接受的 `county_opinion_add` 所在结构。类似错误不能仅靠名字“看起来合理”通过审查。角色 modifier、文化 modifier 和县 modifier 的可用字段分别核对。

强牵制是谁持有、对谁有效必须写清；“封臣得到对玩家的牵制”与“玩家牵制封臣”正相反。永久修正 +999 不代表最终好感面板会显示 +999；基础六维、特质加值和面板值也不同。缩短统治期限的百分比不等于减少等量好感点数。成本放决议 cost 后，不在 effect 再扣一次。

名字库扩充按本文化候选精确过滤，不全局改原版人名或删除已存在角色使用的姓名键。保存双语映射、稳定新增键、原有取名权重和家族名；处理语法约定中的下划线变体，不把展示名直接当无约束内部键。

### 26. 玩家文案别混进实现过程，旧故障别永久占据 README

按钮直说操作与目标，例如“萌战MOD作弊功能”“玩家功绩 +1000”“为皇帝国库增加资金”。失败提示报告实际原因和可操作办法；不加每次都重复的自我辩护。剧情用角色动作、对话和场景推进，数值说明放效果区。

剧情随机化保留相同结算路径，只换已确认的叙事分支。外部模型润色时保留本地化键、变量占位符、语法与目标关系；没有真实调用指定模型，就不声称已由其审稿。

README 放当前用法，MODLOG 放当前证据与历史索引，素材表放来源与身份待确认记录。已解决的凉宫婚约等个案移出当前待办，提炼方法后归档；仍未识别的素材不能作为“冗余”删掉。上传人数和功能从清单/脚本核对，并保持 Markdown 与 Steam BBCode 同文。

### 27. 决议 widget 的控制器必须显式初始化

**1.20.1.1转储确认：** 2026-10-17萌战启动崩溃的致命线程指向竞技场 `mz_ar_host_decision`／`mz_ar_planner`，控制器指针为0，引擎读取空地址而触发 `C0000005`。错误结构为 `widget = { gui = "mz_ar_planner" }`；温泉筹备决议也有相同遗漏。

**正确方式：** 普通自定义筹备界面写 `widget = { controller = default gui = "mz_ar_planner" }`，对应 `gui/decision_view_widgets/mz_ar_planner.gui`。需要专用控制器的界面按同版原生合同显式声明相应类型，不一律改成default。虽然本机 `_decisions.info` 写着默认值default，本次省略字段后对象仍未初始化；不要仅凭文档默认值省略声明。

**维护约定：** 同步修生成源、生成结果与安装副本，并检查具体widget块。启动会加载决议，不能以“尚未点击”为隔离措施；日志最后一条警告也不能替代崩溃栈证据。完整原因、错误/正确示例和防回归方法见[决议控制器启动崩溃案例](../../../skills/linn-modder/anime-strategy-mod/references/ck3-decision-widget-startup-crash.md)。

**验证边界：** 两份决议已修复安装，7项静态检查通过、20存档哈希不变；用户随后确认成功进入游戏并开始游玩，启动及进入游玩已获用户确认。竞技场/温泉筹备UI和完整活动流程尚未单独验收。不把本例推广成所有版本的崩溃原因。

## Project conventions：萌战项目约定，不推广成引擎规则

- 用户要求的是强力可选玩法：不因个人平衡偏好擅自增加费用、冷却、AI 免疫或多重授权。普通机制、作弊入口与调试入口的条件分开。
- 保留稳定人物 ID、已安装角色、存档和源素材。新增人物默认进入专用新开局；另有明确要求才写旧档补入。
- 开局与轮回共用人物配置。人物有强弱项和与原作相符的专属能力，通常包含六维外的效果，不把每人做成同一套满值模板。
- 画像复用和外部补图按本轮授权；早期“不找外部图”“排除整个型月系”后来已有指定作品例外，读取最新范围，不用早期偏好覆盖新要求。
- 正式配偶采用追加关系，保留既有配偶；侧室另算。轮回不迁移孕期，管理权不自动继承婚姻归属。
- 用户接管游戏测试后停止窗口自动化。早期一次 `CloseMainWindow()` 干扰用户加载，造成疑似闪退；这类退出不能当成 MOD 崩溃证据。
- 只问真正改变结果的问题。版本、路径、字段、文件名能从本机查到就先查，不重复要求用户重开或提供同一信息。

## Verification：验证具体行为

| 层次 | 能证明什么 | 不能替代什么 |
|---|---|---|
| 编码、引用、结构、生成一致性 | 产物格式和静态合同 | 引擎解析与作用域实际有效 |
| 安装哈希、descriptor 与播放集 | 目标目录确有这批文件、配置指向它 | 当前进程已经重新加载 |
| 启动日志与主菜单画面 | 本组合本次启动成功 | 结婚、轮回、宣战或 GUI 的全部结果 |
| 同一角色的操作前后、存档字段 | 该操作真实改变了指定对象 | 所有 DLC/政体/角色均兼容 |
| 用户截图和完整操作反馈 | 截图覆盖的界面和流程表现 | 尚未执行的新批次或边界情形 |

小功能用最相关的流程验收，不为了“全绿”重复跑大包。推荐的最小场景：

- **菜单与数值：** 自己和另一角色各一次，切页回来仍指向同一人；暂停/推进时间前后对比。
- **婚姻：** 连续加入第二位配偶，原配偶仍在；侧室与主配偶单独核对，再存读档。
- **轮回：** 死亡、入队、到期、重建、家族与故事、再读档、没有重复化身；不重复杀人代替读档检查。
- **人物与图片：** 一个登记角色、普通 NPC、自创人物和共存 MOD 角色；看真正出问题的控件。
- **战争/救灾：** 目标领国内外各有对象，核对只改变约定范围；涉及 DLC 再补无 DLC 启动。

诊断保留一份有版本和时间的错误基线。优先看本次新增错误、重复频率与调用路径，别只 grep 一个关键字就宣布因果。对本项目曾验证的结果，只记录其覆盖范围；本轮知识整理没有重新启动 CK3。
