# 内容型 MOD 的设计原则

适用于二次元角色替换、UI 皮肤、剧情/技能扩展及包含多类资源的内容 MOD。
按当前问题读取相关章节，确定内容之间的关系、文件的职责和交付方式。
单项修改使用对应规则，完整内容包再组合使用。

## 1. 以完整内容单元组织工作

人物、面板或技能是内容单元；文件只是它们的不同表示。先完成一条可验证的引用链，
再扩大数量。例如角色的名字、头像、模型、技能和剧情引用要一致；UI 按钮的皮肤、
标签、交互状态与点击区域要一致。完成一个单元后，再复用配方批量制作。

把内容理解为依赖图：`稳定 ID → 数据记录 → 展示资源 → 运行时使用点`。
检查新增/覆盖节点及其直接依赖，找缺失引用、重复 ID、未打包资源和意外覆盖。
用现有项目的数据表或资源清单维护这些关系。

## 2. 分清职责，不照搬目录名称

| 职责 | 管什么 | 跨层约束 |
|---|---|---|
| 身份与兼容信息 | mod 身份、发布版本、目标游戏版本、依赖 | 独立记录发布身份、安装位置和各类版本 |
| 内容数据 | 人物、技能、剧情、菜单、语言字符串 | 用稳定 ID 关联，保留目标的合并/覆盖语义 |
| 展示资源 | 图像、模型、声音、字体、动画和 UI 状态 | 与数据约定的名称、参数和资源地址一致 |
| 可编辑源 | 分层美术、编辑器工程和转换配方 | 保留独立可编辑源，并能按配方重新导出 |
| 引擎产物 | 纹理、图集、模型序列化、资源包 | 依据文件头、版本和读取器选择处理方式 |
| 部署与恢复 | 输出清单、安装映射、覆盖范围、撤销方式 | 通过配置解析安装位置，内部引用保持相对路径 |

这些是逻辑职责，小型项目可以共用目录。优先沿用游戏或官方编辑器已有布局，
只在职责混淆导致真实问题时拆分。加载顺序和依赖解析按目标机制单独验证。

## 3. 用稳定标识关联，用显示名呈现

保留引用既有内容所需的原始 ID；新增内容按目标规则分配命名空间、项目后缀或其他
唯一标识。更新既有内容时沿用其 ID，跨表匹配也使用 ID。
根据目标支持的 ID 类型选择字符串命名空间、数值区间或编辑器分配机制。

换角色时，沿 ID 检查图标、模型、技能、语音、关系和剧情；换 UI 时，检查控件、
状态图、字体、语言键和事件绑定。批量修改前先验证一个完整单元，确保未改引用保留。

## 4. 用目标资源合同约束美术与数据

同一角色在头像、半身图、全身图、模型中可以有不同输出，但应来自一致的角色设定。
共享色板、比例和服装版本；每个输出分别满足画布、裁切安全区、alpha、pivot、
图集和渲染要求。UI 还需要检查缩放、文字长度和状态切换。

先确认消费方、版本和方言，再选编辑器或 writer；保留未知字段、精度、编码和未改资源。
按文件头和结构识别格式，分别验证读取、写入及回封能力。解析失败时记录具体位置，
对照目标读取规则定位差异；确认规则后进行局部修改，再检查往返结果。

## 5. 分开记录版本，再判断兼容性

游戏 build、loader/SDK、编辑器、数据 schema、资源编译版本和 mod 发布版本分别记录。
以消费方能否读取产物为判断依据，记录已验证的版本范围。
涉及首次工具选择或升级时，联网核实对应版本的原文。

游戏升级后比较受影响的字段、ID 与资源依赖，避免用整份旧数据覆盖新版本新增内容。
优先目标支持的增量覆盖；若只能整文件替换，列明覆盖范围与冲突条件。
分别处理 ID 冲突、共享文件覆盖、加载顺序和行为冲突。

## 6. 将下载、部署和启用分开

内容可能来自工坊、手动压缩包、编辑器导出或加载器目录。
分别检查内容取得、依赖部署、游戏启用和功能运行，明确每一步的输入与输出。

发布时区分主包、必需依赖与可选组件；说明每个组件的用途、来源、版本及相对目标。
按实际需要记录 `组件 → 逻辑目标 → 覆盖文件 → 前置条件 → 校验方式 → 恢复方式`。
沿用项目现有清单格式表达这些信息。

游戏根、mod 根、存档根和工作区在执行时从用户配置或目标元数据解析。
内部引用使用相对路径或资源 ID；缺少必要位置时获取目标信息。
外部安装映射与内容数据分离，发布清单只收录交付所需的文件。

## 7. 让修改能够验证和撤销

最小过程是：只读识别 → workspace 副本 → 验证原样读写 → 修改一个内容单元 →
检查引用和产物 → 按授权部署/运行 → 保留恢复能力。
文本检查数据及编码，图像检查渲染属性，容器检查结构、条目和未改载荷。

根据任务选择验证层级：源素材编辑、格式检查、资源加载、实际行为。
记录各层的检查结果，验证判据可按需参考[验证方法](oracles-how-agents-know-a-mod-works.md)。
