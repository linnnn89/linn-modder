# CK3 运行维护与活动优化

用于推进时间卡顿、重复事件、周期维护、原生机制替代，以及邀请—旅行—活动—结算流程的设计与复核。先定位相关入口和直接调用链，不从全项目扫描开始。

**依据与边界：** 2026-10-17 的工作经验，以本机 CK3 1.20.1.1 原生说明、脚本、故障日志和定向脚本检查为依据。下文的命令数量是固定场景的离线计数，性能优化尚无游戏耗时实测；不能把这些结论写成“卡顿已解决”。具体规则以目标版本为准。

按当前问题读取：

- [定位成本](#定位成本)：区分错误刷屏、调用次数与实际耗时。
- [选择实现方式](#选择实现方式)：原生状态、事件和必要补漏的分工。
- [维护生命周期](#维护生命周期)：登记、轮回、关系、归队与差量更新。
- [原生活动流程](#原生活动流程)：邀请、旅行、到场、阶段、奖励和取消。
- [验证与交付](#验证与交付)：测试模型、生成源和定向安装。

## 定位成本

1. 从当前会话日志、相关 `on_action`、story cycle、决议/互动 AI 检查和活动回调入手。区分加载时一次运行、全局周期、每个角色的周期，以及真正发生变化时的通知。
2. 写清粗略成本：**入口频率 × 执行对象数 × 每次嵌套工作量**。外层已经遍历登记人物，内层又逐项查整个身份表，会把线性工作放大成近似平方量；已知角色键或组键时应直接验证对应槽位。
3. 统计日志时保留来源。历史错误条数不等于回调次数；`Unknown` 不能据此归给本 MOD。先消除有明确来源的无效引用、缺失变量比较及其重复输出，不为清空日志删除相关功能。
4. 查看条件检查本身的代价。给全量循环加“已经处理”条件，只减少循环内的写入，不一定减少遍历；写入前判定不变，也不等于没有成本。

降低频率不能单独证明安全：若修正只持续 8 日，巡检从 7 日改为 30 日会产生空档。须同步决定有效期、失效时机和漏接通知后的最长恢复时间；这些数值是机制设计，不是所有 MOD 通用的默认值。

## 选择实现方式

优先考虑 **原生持久数据/规则 → 生命周期事件 → 有界目标集合或待办队列 → 必要的周期补漏**。每一步都要求与原玩法的对象、方向、时效和条件相符。

| 需求 | 优先方案 | 不应偷换的语义 |
|---|---|---|
| 固定父母、性格、已有特质经验 | 历史/创建/首次登记时赋值，由人物状态保存 | 每周重设会覆盖游戏中的正常变化 |
| 普通人物的默认外观 | 核对文化 ethnicity 等原生默认值，必要时在出生/创建时修正 | 不删除框架 2D 人物的独立立绘分支；不为少数人物修改全文化 |
| 文化间人物好感宽容 | 本版原生文化修正可表达时直接使用 | `ignore_negative_culture_opinion` 与 `ignore_negative_opinion_of_culture` 有方向；人物好感豁免不等于文化接受度数值或混合文化资格 |
| 条件性人物奖励 | 常驻 modifier，资格变化时添加/撤销，稳定状态不续期 | 全文化奖励不等于只奖励符合资格的玩家或统治者；须覆盖失去资格的入口 |
| 领国网络收益 | 按加入、离开、易主、方案变化做差量同步 | 单建筑或县域修正不一定等价于全领国网络 |
| 旧版身份/家族迁移 | 有明确兼容需求才保留；退役需符合用户范围 | “执行一次”不代表仍有必要；建立新运行索引也不等于恢复旧档身份 |

只有功能需要持续强制规则时，才持续维持它。原作初始友谊、配偶、竞争关系与游戏中自然演化的关系分开；用户允许自由演化时，不用后台维护把结果每周改回。旧效果 ID 可能被延迟事件或外部 MOD 引用，删除入口与删除定义不是同一项操作。

## 维护生命周期

### 登记与轮回

- 区分稳定人物键、当前化身、等待重建槽位和存活保护集合。首次登记或化身变化才执行初始化；同一化身再次登记不重复发奖励或重建关系。
- 轮回等待队列按槽位去重。冷却在入队时确定，重试不能不断重置；创建失败仍能重试。已创建有效化身时应停止重建。
- 只恢复本次化身涉及的关系。动态父母也能轮回时，在孩子或父母登记时更新引用，覆盖父母先到、孩子先到以及引用缺失；不借此恢复全体关系。
- 死亡后的延迟任务不要依赖已死亡角色继续充当执行者；管理者更换后使用当前有效管理者。相关持久队列须考虑存读档，临时回调列表则不应升级成永久全局缓存。
- 避免遍历同一变量列表时删除或重新入队：先取快照，或收集需要删除的项，遍历结束后再写入。只为此功能所需的集合建索引，不能为了“优化”再引入更大的全世界同步器。

### 事件过滤、请求合并与差量写入

- 全局领主/封臣变化等通知先做便宜的关联过滤；只处理与目标领国、旧领主或场馆持有者有关的事件。检查本版入口究竟提供哪些 scope，缺失的旧领主不能直接解引用。
- 同组归队等连续请求可合并为一次延迟处理。执行前占用请求标记，执行结束释放，并设计失败或管理者变化后的恢复；不能把持久标记留成永久锁。
- 登记时已有组键，可用原生 `switch` 分派代替逐组成员判断；不据此声称引擎内部实现必然是 O(1)。
- 原生婚姻限制与结婚/纳妾回调可以承担正常路径；若本版没有确认覆盖订婚等情况的通知，保留只针对相关人物的补漏。不要为了“零轮询”放弃承诺的保护。
- 稳定网络只补缺失效果、撤销已离开的对象、替换真正改变的方案，不先全撤再全加。固定 10 个伯爵领/30 个省份的案例中，稳定同步的 modifier 添加/移除命令由 103 条降至 0 条；成员遍历仍存在。
- 原生共享 flag 可能由多个系统设置。不要随意清除或永久化；确需续期时，将有效期与维护间隔配套，说明恢复延迟的变化。

## 原生活动流程

### 明确回调的对象和顺序

以目标版本 `common/activities/activity_types/_activity_type.info` 为准。本次 1.20.1.1 的合同如下，不能仅按回调名称猜 scope：

| 入口 | root | 适合的责任 |
|---|---|---|
| `on_start` | activity | 建立本届状态；在正式创建时消耗场馆年度次数 |
| `on_enter_active_state` | character | 实际进入活动后的个人登记；同场重复进入仍须防重 |
| `on_phase_active_activity` | activity | 所有参与者的 `on_phase_active` 运行后，执行一次阶段工作与推进调度 |
| 阶段 `on_end` | character | 按主办者或共享结算标记选唯一结算入口；不是天然只调用一次 |
| `on_complete` | character | 按设计处理最终完成或补充清理；不与阶段结束重复发奖 |
| `on_invalidated`、`on_host_death` | activity | 一次性取消与清理；保留已合法取得的长期收益 |

对于必须在仍有效的参赛名单上排名的活动，可以在末阶段 `on_end` 结算、在 `on_complete` 仅作兜底清理。**这是一种实现选择，不是所有活动都应禁止在 `on_complete` 发奖**；原生宴会就有完成回调结算。若只让主办者处理末阶段，须考虑主办者死亡或缺席的取消路径。

### 邀请与旅行

- 使用原生 `guest_invite_rules` 构建邀请名单，保留原生接受、旅行与到场流程。邀请名单不是实际到场名单；不以传送或直接登记代替真实参会。
- 保留优先级。主办者战争、最高领主战争和邻国关系可能指向同一个领主；在同一邀请上下文内对本人及其随员展开去重，先筛有效候选，再取人数上限。不要假设不同规则间一定共享临时列表。
- 原生基础 `can_be_activity_guest` 仍参与判断；活动自己的高接受率不保证敌国 AI 一定来。区分“有邀请入口”“满足资格”“接受”“完成旅行”四层证据。
- 地点过滤使用能覆盖玩法的最小范围。RICE 曾将温泉的省份过滤从 `all` 缩小到领国/住所范围以减少开销；已有 `domain` 限制的活动无需重复改造。
- AI 意图目标列表设合理上限，不对世界人物展开。上限与人数、剧情覆盖是设计取舍，不因性能目标擅自减少用户要求的来宾规模。

### 到场、互动与奖励

- 区分受邀、travel、passive、active、离场和历史参与者。原生说明将 passive 定义为到达后等待阶段开始；active 才是参与当前阶段。不要把“到达地点”与“进入活动”当成相同回调。
- attending 迭代器中的人物仍需检查本届归属；需要正在参赛时再检查 active。结算回调时的状态可能正在转换，不能机械地给所有结算条件都加 active，须核对回调顺序。
- 已有原生进入活动登记，就不要每阶段再全员尝试同一登记。后续轮次可遍历冻结的选手名单；疗养活动则允许迟到者通过相同到场回调登记。两种规则不可混为通用模板。
- 全员互相好感确实需要成对效果时，保留玩法成本。新来宾只遍历先前登记且仍在场的人，每对双向写入一次，再加入名单。全员始终在场的 101 人案例中，候选检查从 10,201 降为 5,050，10,100 条有方向好感效果不变；此算法仍是 O(n²)，不是线性优化。
- 若一批 AI 容易向同一个人集中发互动，可限制每人每阶段的接收次数，在发出事件前记录，再选择其他合适目标。发起次数、接收次数和同意建立关系分别设计；这会改变互动分配，须符合用户玩法要求。
- 在奖励或弹窗前提交本届防重标记，延迟选项执行时重新检查归属、阶段和取消状态。排名奖励发给获奖人物，不能因他们是 AI 或外国角色而改发给主办者。
- 无伤比赛应检查整个直接调用链及可选意图，不只搜索顶层事件。不要调用带伤亡的原生决斗后再“补血”；比赛无伤不自动意味着往返旅行或活动之外的自然死亡也被禁用。

### 关闭、取消与治疗

关闭和取消都应能安全重复调用。只清理仍由本届持有的临时人物状态；不得擦除另一活动的新状态。清理后释放名单，已关闭活动的迟到回调不能重新登记或发奖。

治疗和防病应区分直接效果、延迟通知、内层共用效果与提示框求值。若疾病保护必须拦截原生入口，应保证一次感染尝试只随机一次，跨延迟事件传递的许可在使用后清除，不泄漏给后续调用。说明其他 MOD 直接赋疾病 trait 的绕过边界，并核对原生覆盖的版本兼容性；不能用健康加成冒充指定的感染概率降低，也不能借性能优化改变治疗范围。

## 验证与交付

- **先证实语义，再写测试替身。** 官方说明明确：trigger 中 `?=` 的左侧不存在时返回 false，effect 中则跳过该 scope。不要把它实现成“缺失即 true”，也不要从错误替身产生的失败推断原脚本存在漏洞。数值缺失、对象 scope 和列表生命周期同样要有依据。
- 场景解释器应拒绝未知命令，明确哪些原生调用只是边界桩。优先检查一次完整流程，以及确实受影响的重复、取消、离场、管理者切换等场景；不能把自己编写的调度模型当作引擎调度证据。
- 区分静态复杂度估算、生成脚本操作计数、引擎计时和人工游玩。未运行游戏时，不宣称 AI 旅行、回调顺序、旧档读写或推进速度已验证。
- 同步修改生成源和相关覆盖层；只重建受影响输出。生成器可能导出整套人物/画像，不能为几行脚本启动完整重建。安装副本有独立修改时按原基线分别打补丁，不直接用源目录覆盖。
- 验证只围绕变更文件、直接调用链和相关检查。使用写入白名单、受影响文件备份、安装前基线和安装后定向核对；禁止在生成、打包、安装各阶段反复枚举或哈希全项目。明确要求的存档保护核对单独保留。
- `--suppress` 等过滤诊断不缩小底层扫描。脚本默认全量验证也不是扩展范围的理由；通过的检查在相关内容没变时不重复跑。详见[验证范围](verification.md)。

决议控件初始化与启动故障另见[控制器案例](ck3-decision-widget-startup-crash.md)。玩家说明先写实际收益、费用、耗时与后果，不用防御性实现备注代替效果说明。
